# Architecture Decision Records

Важные/масштабные решения в рамках данного репозитория.

### ADR-001. Организация модулей внутри ограниченного контекста

Статус: **устарело** (см. ADR-003)

#### Контекст

В каждом ограниченном контексте (bounded context) нужно зафиксировать единый подход к разбиению на модули, чтобы сохранить чистую архитектуру, контролировать зависимости и не скатиться в спагетти-код.

#### Решение

Гранулярная модульная структура: под каждый слой чистой архитектуры и каждый адаптер создаётся отдельный Gradle-модуль. Доступность между модулями настраивается через Gradle, поэтому недопустимые связи отсекаются уже на этапе компиляции.  
Пример набора модулей в ограниченном контексте:
- domain
- usecase
- rest
- database
- config

#### Плюсы

- Жёсткие границы модулей - недопустимые связи между слоями и адаптерами не компилируются.
- У каждого модуля свой минимальный набор зависимостей - сразу видно, от чего он зависит.
- Отдельные слои проще тестировать изолированно.

#### Минусы

- Много модулей на каждый контекст - большое количество Java-пакетов и Gradle-файлов.

### ADR-002. Способ взаимодействия двух ограниченных контекстов

Статус: **принято**

#### Контекст

Есть два ограниченных контекста: Лобби и Игра.  
В Лобби игроки настраивают игровую партию, затем начинают её. В Игре происходит непосредственный игровой процесс.  
Необходимо определить способ взаимодействия между этими микросервисами.  
Примечание: инициализация активной игровой партии может затягиваться. При этом игроки могут ожидать начала игры, находясь некоторое время в Лобби.

#### Решение

Событийно-ориентированное взаимодействие через Apache Kafka.  
В Лобби происходит событие "Партия начата".  
В Игре активируется создание активной партии при получении события.

#### Плюсы

- Отказоустойчивость и масштабируемость.
- Демонстрация событийной интеграции с Kafka между микросервисами (ключевой плюс в рамках демо-приложения).

#### Минусы

- Необходимость поддерживать инстанс Kafka.
- Сложное интеграционное тестирование.
- Сложная реализация и конфигурация по сравнению с REST или RabbitMQ.

### ADR-003. Реорганизация модулей ограниченного контекста

Статус: **принято**

#### Контекст

Гранулярная модульная структура из ADR-001 существенно усложняет работу над небольшим проектом, а её преимущества не окупаются.

#### Решение

Упростить модульную структуру ограниченных контекстов:
- **domain** - модель предметной области; остаётся отдельным модулем со строгой изоляцией.
- **app** - единый модуль для use case и всех адаптеров, разделённый по пакетам:
  - `config` - конфигурация;
  - `usecase` - сценарии;
  - `input` - входные адаптеры;
  - `output` - выходные адаптеры.
- **restapi** - отдельный модуль с описанием интерфейсов REST API для переиспользования при реализации веб-клиентов.

Контроль связей между слоями выполняет ArchUnit (проверки запускаются на этапе тестов, а не компиляции).

#### Плюсы

- Менее строгая структура упрощает разработку в условиях небольшого размера проекта.
- Меньше Gradle-файлов и папок в проекте.

#### Минусы

- Нарушения архитектурных связей не выявляются на этапе компиляции - только через тесты ArchUnit.
